## Prerequisites

| Requirement | Details |
|---|---|
| **GitHub Account** | Admin access to your repository |
| **Snowflake Account** | Active Snowflake account with appropriate role permissions |
| **API Integration** | `GITHUB_API_INTEGRATION` configured in Snowflake |
| **Snowflake Warehouse** | Dedicated warehouse (e.g., `COMPUTE_WH`) |
| **Database** | Target database (e.g., `ECOM_DB`) with target schema |
| **Python** | 3.12+ (managed by GitHub Actions runner) |

## Step 1: Configure GitHub Secrets

Navigate to your repository → **Settings** → **Secrets and variables** → **Actions** → **New repository secret**.

Add these **7 secrets**:

| Secret Name | Description | Example Format |
|---|---|---|
| `SNOWFLAKE_ACCOUNT` | Your Snowflake account identifier | `<org>-<account>` (e.g. `MYORG-MYACCOUNT`) |
| `SNOWFLAKE_USER` | Snowflake deployment username | `dbt_service_user` |
| `SNOWFLAKE_PASSWORD` | Snowflake user password | `••••••••••••` |
| `SNOWFLAKE_ROLE` | Snowflake role to execute dbt | `ACCOUNTADMIN` or `DBT_ROLE` |
| `SNOWFLAKE_WAREHOUSE` | Virtual warehouse to use | `COMPUTE_WH` |
| `SNOWFLAKE_DATABASE` | Target database | `ECOM_DB` |
| `SNOWFLAKE_SCHEMA` | Target schema | `RAW` |

> ⚠️ **Never** commit credentials to the repository. The pipeline uses `::add-mask::` to prevent credentials from appearing in logs.

## Step 2: Set Up Branch Protection

Navigate to → **Settings** → **Branches** → **Add branch protection rule**.

### Configure these settings:

| Setting | Value |
|---|---|
| **Branch name pattern** | `main` |
| **Require a pull request before merging** | ✅ Enabled |
| **Required approvals** | `1` |
| **Dismiss stale pull request approvals** | ✅ Enabled |
| **Require review from Code Owners** | ✅ Enabled |
| **Require status checks to pass** | ✅ Enabled |
| **Status checks that are required** | `🏗️ dbt Compile & Build` |
| **Require branches to be up to date** | ✅ Enabled |
| **Do not allow bypassing** | ✅ Enabled |

This ensures:
- **Every PR requires Vilas Sonje's approval** (via CODEOWNERS)
- **CI must pass** before merge is allowed
- **No direct pushes** to `main`

## Step 3: Verify Snowflake Integration

Your Snowflake `GITHUB_API_INTEGRATION` is already configured. Verify it:

```sql
-- Check API integration
SHOW INTEGRATIONS LIKE 'GITHUB%';

-- Verify permissions
SHOW GRANTS ON INTEGRATION GITHUB_API_INTEGRATION;
```

The CD pipeline will automatically:
1. Create the Git Repository object (if it doesn't exist)
2. Fetch latest code
3. Create/update the dbt Project
4. Run `dbt build`

## Step 4: Test the CI Pipeline

### 4.1 Create a feature branch

```bash
git checkout -b feature/test-ci
```

### 4.2 Make a small change

Edit any file in `generated_projects/retail_dbt_v1/`, e.g., add a comment:

```bash
echo "-- CI test comment" >> generated_projects/retail_dbt_v1/models/staging/stg_ecom__customers.sql
```

### 4.3 Push and create PR

```bash
git add .
git commit -m "test: verify CI pipeline"
git push origin feature/test-ci
```

Then create a Pull Request to `main` on GitHub.

### 4.4 Verify

- Check the **Actions** tab for the CI workflow
- Review the **SQLFluff** annotations on the PR
- Verify the **dbt build** check passes/fails
- Confirm the **merge button** is blocked until CI passes and you approve

---

## Step 5: Test the CD Pipeline

After CI passes and the PR is approved:

1. **Merge** the PR into `main`
2. The CD pipeline triggers automatically
3. Check **Actions** tab for `CD – Deploy to Snowflake`
4. Verify in Snowflake:

```sql
-- Check the Git Repository was created
SHOW GIT REPOSITORIES IN SCHEMA ECOM_DB.RAW;

-- Check the dbt Project
SHOW DBT PROJECTS IN SCHEMA ECOM_DB.RAW;

-- Verify the data
SELECT * FROM ECOM_DB.RAW.dim_customers LIMIT 10;
SELECT * FROM ECOM_DB.RAW.fct_orders LIMIT 10;
```

## Pipeline Details

### CI Pipeline (`.github/workflows/ci.yml`)

| Job | Steps | Purpose |
|---|---|---|
| **lint-sql** | SQLFluff lint | Static analysis of SQL files |
| **dbt-validation** | deps → parse → compile → build | Full dbt validation against Snowflake |

**Triggers:** Pull requests targeting `main` that modify `generated_projects/retail_dbt_v1/**`

### CD Pipeline (`.github/workflows/cd.yml`)

| Step | Description |
|---|---|
| **Create Git Repo** | `CREATE GIT REPOSITORY IF NOT EXISTS` (idempotent) |
| **Fetch** | `ALTER GIT REPOSITORY ... FETCH` pulls latest code |
| **Create dbt Project** | `CREATE OR REPLACE DBT PROJECT` from Git stage |
| **Execute** | `EXECUTE DBT PROJECT ... ARGS = 'build'` |
| **Report** | Query history & step summary |

**Triggers:** Push to `main` (after merge) that modifies `generated_projects/retail_dbt_v1/**`

### Deployment Script (`scripts/snowflake_deploy.py`)

The Python script handles:
- Secure credential management via environment variables
- Idempotent object creation (`IF NOT EXISTS`, `OR REPLACE`)
- Detailed logging with emoji markers
- JSON results file for audit trail
- GitHub Actions step summary integration
- Proper error handling and exit codes

## Troubleshooting

### CI: "Could not find profile named 'ecom_profile'"

The CI pipeline generates `profiles.yml` dynamically with the correct profile name `ecom_profile`. If this error occurs:
- Verify the `dbt_project.yml` has `profile: 'ecom_profile'`
- Check that the CI workflow's `Generate CI profiles.yml` step ran successfully

### CI: dbt build fails with Snowflake connection errors

- Verify all GitHub Secrets are set correctly
- Check that `SNOWFLAKE_ACCOUNT` uses the format `<organization>-<account>` or `<locator>.<region>`
- Ensure the Snowflake user has permissions on `ECOM_DB`

### CD: "Object 'GITHUB_API_INTEGRATION' does not exist"

- Verify the API integration exists: `SHOW INTEGRATIONS LIKE 'GITHUB%';`
- Ensure the Snowflake role used has `USAGE` privilege on the integration

### CD: "Git repository fetch failed"

- Verify the GitHub App is authorized in Snowflake
- Check if the repository URL is correct in the CD workflow
- Try manually: `ALTER GIT REPOSITORY ECOM_DB.RAW.DBT_PROJECT_FACTORY_REPO FETCH;`

### CD: "dbt Project creation failed"

- Verify the dbt project files exist at the expected path in the repo
- Check that `dbt_project.yml` is committed (not in `.gitignore`)
- Ensure the Git repository was successfully fetched

### General: "Resource exhausted" or rate limit errors

- The free-tier Gemini API has daily limits (this affects the app, not CI/CD)
- CI/CD uses Snowflake directly, not the Gemini API

## Security Considerations

| Measure | Implementation |
|---|---|
| **Credentials in GitHub Secrets** | Never hardcoded; always from `${{ secrets.* }}` |
| **Log masking** | `::add-mask::` hides credentials in workflow logs |
| **profiles.yml** | Generated dynamically in CI; real file is `.gitignore`d |
| **CODEOWNERS** | All changes require `@SonjeVilas` approval |
| **Branch protection** | No direct pushes to `main`; CI must pass |
| **Idempotent deployment** | `IF NOT EXISTS` and `OR REPLACE` prevent duplicates |
| **No secrets in deploy script** | All credentials via environment variables |
